## Dispatch and module isolation

Plain public request records/classes and public conventional handler methods are supported; Wolverine requires neither MediatR request interfaces nor an `IHandler<T>` interface. `IMessageBus.InvokeAsync(request, cancellation)` supports a no-response use case; `InvokeAsync<TResponse>` returns the requested response. The requested response is suppressed from cascading publication. Keep Contract requests and response DTOs implementation-free and Application handlers behind their established boundaries. Rich/anemic domain shape and distinct read/write models remain application decisions. [Pinned handler documentation](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/handlers/index.md), [dispatch API](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/IMessageBus.cs), [typed invocation implementation](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Runtime/Handlers/Executor.cs#L178).

The runtime selects an invoker **by CLR message type across the host**. Scanning separate Application assemblies is not a separate dispatcher namespace or a runtime security boundary. Give each module its own command/query types and require exactly one owning use-case handler per request. Reject missing/duplicate command/query registrations in architecture/startup checks. Duplicate event subscribers are a different concern and require explicit transaction/delivery routing. [MessageBus](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Runtime/MessageBus.cs#L117), [invoker selection](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Runtime/WolverineRuntime.cs#L351).

Handler discovery uses an assembly allowlist and can be made explicit with `DisableConventionalDiscovery()` and `IncludeType<T>()`. Module composition should contribute its selected handlers and middleware; the host builds the single runtime and transport configuration. Explicit discovery avoids unintentionally scanning direct-service classes and hidden handlers. Set the application assembly explicitly in multi-host tests to avoid the documented process-wide discovery cache trap. [Pinned discovery guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/handlers/discovery.md).

`InvokeAsync` may otherwise perform remote request/reply. The proposed catalog recipe sets **`EnableRemoteInvocation = false`**, keeps CQRS requests local, and allows externally routed messages only through the established fact-publication adapter. Do not silently turn commands into interservice messages. Retain the prohibition on command/query/handler chaining; framework support for it does not change that architecture decision. [Pinned sending guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/messaging/message-bus.md).

For multiple event handlers, v6's classic default combines methods into one logical handler; `MultipleHandlerBehavior.Separated` creates independent queues/transactions. This setting is **not** a substitute for the explicitly atomic transactional-module-event path, nor does the default prove that multiple EF contexts participate atomically. The upstream modular-monolith guide primarily recommends asynchronous communication, so its sample cannot simply replace the retained shared-transaction design. [Pinned modular-monolith guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/tutorials/modular-monolith.md), [handler graph default](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Runtime/Handlers/HandlerGraph.cs#L79).

## Automatic module-local authorization

Wolverine's generated middleware supports a `BeforeAsync` method, dependency injection and a per-chain filter, so a module-local pipeline adapter can run Application-owned checks before every command/query handler. The filter must cover **all owning module request types**, including no-response commands and non-HTTP invocations, and missing authorization configuration must fail closed. A module-local registry/convention is sufficient; the deferred generic policy-bearing declaration framework need not return. Throw an explicit denial/unavailable-facts exception before protected behavior; map it at the outer boundary and exclude denial from transient retry policy. These are proposed catalog rules, not built-in Wolverine guarantees. [Pinned middleware guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/handlers/middleware.md), [middleware construction](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Middleware/MiddlewarePolicy.cs).

HTTP authorization alone cannot supply this guarantee to internal calls. A particularly relevant integration hazard is **scope/caller propagation**: inline invocation obtains a new `MessageContext`; generated code may create a child service scope from the root, with special handling to prime Wolverine's message context. This does not establish reuse of arbitrary HTTP-scoped caller-context services. Neither a tenant header nor `UserName` establishes trusted permissions or user authority. [Inline executor](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Runtime/Handlers/Executor.cs#L139), [scope-local carrier](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Runtime/ScopedMessageContextHolder.cs), [scope priming](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Runtime/Handlers/PrimeScopedMessageContextFrame.cs).

The recipe therefore needs a trusted caller-context handoff established at HTTP authentication or the non-HTTP invocation boundary, independent of the generated DI scope. One candidate is an Application-owned immutable caller snapshot accessed through an async-flow carrier, established and cleared by boundary adapters; another is an explicitly bound invocation adapter. Whichever is chosen must be proven with concurrent callers, missing context and background/service calls. Do not pass caller-selected permissions in request payloads or blindly trust broker headers. No runtime proof for either mechanism was run here.

Direct-service modules retain Application-owned service interfaces, acyclic reuse and **decorators** enforcing the same checks. They need no CQRS dispatch dependency simply because another module uses Wolverine. A module using durable event publication may depend on an Application-owned narrow publication/transaction interface implemented in Infrastructure; concrete EF, relational outbox and transaction coordinator types stay there. Domain and Contract do not acquire Wolverine dependencies. This is the proposed architecture mapping against the retained [application-flow decision](https://github.com/lewan0996/arch-patterns/issues/18#issuecomment-5849516623) and its [authorization amendment](https://github.com/lewan0996/arch-patterns/issues/18#issuecomment-6884959476).

## Minimal generation and proof implications

Wolverine 6 separates runtime compilation from core: Dynamic/Auto operation requires `WolverineFx.RuntimeCompilation`; a Static deployment with generated code compiled into the host can omit it. Specify the build/code-generation lifecycle in the template recipe and validate both the generated registration and production mode. A dependency restore alone misses this startup failure. [Pinned code generation guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/codegen.md).

The smallest useful dispatch proof uses two modules in one host: a response-bearing query, a response-bearing command, a no-response command, an allowed and denied caller, a missing-context call, and the direct-service decorator equivalent. Exercise both HTTP mapping and an actual internal/background invocation; concurrent calls must not share caller facts. Check that a missing/duplicate handler and a request accidentally mapped remotely fail, event subscribers do not accidentally execute as CQRS handlers, and production generated code starts. These are acceptance conditions for a cheap proof, not completed evidence. Provider/transport durability proofs belong to the companion investigations.

## Comparison and recommendation boundary

- **Wolverine 6.64.0:** MIT and current maintenance, covering both dispatch and messaging. It adds convention/code-generation and caller/transaction handoff obligations. Documentary dispatch fit is good; atomic multi-context integration and the concrete security adapter remain proof gates.
- **MediatR 12.5.0 plus MassTransit v8:** preserves the prior package-specific recipes, but MediatR's vendor explicitly provides no support/security updates for pre-commercial versions; MassTransit's vendor says v8 support ends **2026-12-31**. The prior v12.5 license is Apache 2.0, not MIT. Keeping this pair is a conscious maintenance choice, not a low-risk evergreen default. [Pinned MediatR license](https://github.com/LuckyPennySoftware/MediatR/blob/8a64581e2570e7410c5f44835d9ea112beccbe6b/LICENSE), [vendor FAQ](https://luckypennysoftware.com/faq), [MassTransit vendor support statement](https://massient.com/), [v8 Apache license](https://github.com/MassTransit/MassTransit/blob/v8.5.10/LICENSE).
- **Small dispatcher/permissive fork:** may address mediator maintenance or API preference, but does not supply durable messaging or remove the cross-module transaction work. There is no evidence from this research that justifies owning a fork before testing the leading integrated candidate. This is an inference from scope, not a benchmark or a completed fork assessment.

Recommendation for the live discussion: keep Wolverine as the preferred candidate, resolve the explicit transaction and caller-context integration seams, and claim verified support only after the bounded proof. Do not translate the old MediatR pipeline/MassTransit outbox API names mechanically or promise feature equivalence.

No application was compiled or executed, no production templates were implemented, and no framework selection was made by this research.
