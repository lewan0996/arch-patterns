# Wolverine durable messaging fit

Research for [Investigate a minimal dispatcher, MediatR fork or Wolverine](https://github.com/lewan0996/arch-patterns/issues/37), checked 2026-11-15. This is documentation and source evidence, not a framework selection or a claim that generated applications have passed runtime checks.

## Version and evidence boundary

The examined release is **Wolverine 6.64.0**, tag `V6.64.0`, commit `ccdf32562f6f53f01863d9fbb14886b8213f3ee2`, released 2026-11-09. Its source targets .NET 9 and 10. Do not select the numerically greatest tag blindly: the repository also contains misleading historical `V7.*` tags. Hosted documentation follows development; the source links below pin the examined release. [Release](https://github.com/JasperFx/wolverine/releases/tag/V6.64.0), [build properties](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/Directory.Build.props).

The source contains relational persistence, EF integration and broker tests, but their existence does not establish that they were run successfully in this session or that the catalog's combination has been verified. In particular, the Azure transport test helper connects to **the Service Bus emulator**. The emulator differs from the managed service and does not preserve data/entities across its own restart. [Pinned test helper](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Transports/Azure/Wolverine.AzureServiceBus.Tests/AzureServiceBusTesting.cs), [Microsoft emulator limitations](https://learn.microsoft.com/en-us/azure/service-bus-messaging/overview-emulator).

## Assessment

Wolverine has documented and implemented building blocks for dispatch plus durable messaging on both retained transports and database engines. It is a plausible replacement for the prior MediatR/MassTransit combination. Those blocks do **not** by themselves prove the retained cross-module transaction contract, module isolation, or every crash boundary. The cross-context coordination design needs separate evaluation, and executable support requires the proof set below. The narrower claim supported here is that Wolverine can transactionally persist an EF context's state, its handled-message marker and outgoing envelopes, with durable background delivery and framework failure storage. [Pinned EF transaction implementation](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/Internals/EfCoreEnvelopeTransaction.cs).

## State, outbox and inbox

Wolverine EF transactional middleware enrolls a selected `DbContext` into messaging. With Wolverine envelope mappings, pending envelopes are tracked entities; without mappings, persistence uses the context's connection and transaction through ADO.NET. `EfCoreEnvelopeTransaction.CommitAsync` records completion, flushes tracked changes when necessary, commits, and only then flushes outgoing messages. This ordering is evidence for one selected context; it does not automatically enroll another context or make another database atomic. [Pinned EF inbox/outbox guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/durability/efcore/outbox-and-inbox.md), [transaction implementation](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/Internals/EfCoreEnvelopeTransaction.cs).

Outgoing subscriber endpoints must explicitly use durable outbox mode; merely configuring database storage is insufficient. Incoming fact-event destinations likewise need a durable inbox. A local asynchronous route writes an incoming envelope rather than requiring a broker trip. Buffered in-memory endpoint modes are unsuitable for the retained crash-survival requirement. [Pinned durability guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/durability/index.md), [EF inbox/outbox guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/durability/efcore/outbox-and-inbox.md).

For a single-context operation, the direct-service profile can use `IDbContextOutbox<TContext>` without turning its use cases into Wolverine handlers. Enroll before publishing; commit through its save-and-flush operation. This preserves the possibility of using Wolverine only as the reliable publication adapter for direct services. A shared cross-module operation instead needs the outer coordinator described in [the transaction investigation](wolverine-transactions.md); participants must not invoke this independently committing helper. Repeated flushes on one scoped outbox default to `MultiFlushMode.OnlyOnce`; an explicit batching implementation must deliberately use `AllowMultiples`. [Pinned API](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/IDbContextOutbox.cs), [usage and multi-flush guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/durability/efcore/outbox-and-inbox.md).

PostgreSQL and SQL Server have separate relational message-store implementations and inbox schemas. EF source contains SQL Server envelope-persistence tests and a PostgreSQL EF integration setup test. These support availability of the integrations, not an inferred complete production-broker/provider matrix. Database storage must coincide with the business transaction for atomic state/outbox and completion writes; an ancillary store with another database does not magically join the main store's transaction. [PostgreSQL inbox schema](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.Postgresql/Schema/IncomingEnvelopeTable.cs), [SQL Server inbox schema](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.SqlServer/Schema/IncomingEnvelopeTable.cs), [SQL Server EF test](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/EfCoreTests/persisting_envelopes_with_sqlserver.cs), [PostgreSQL EF test](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/EfCoreTests/Bug_661_postgresql_with_ef_core.cs).

Successful outgoing sends cause durable outgoing rows to be deleted, consistent with the amended catalog policy requiring no sent-event archive. Failed/unconfirmed sends remain eligible for recovery. Do not configure delivery-expiry/TTL behavior that silently abandons old unconfirmed facts; Wolverine also has expiration paths, so this must be an explicit recipe restriction and verified behavior. [Pinned durable sending agent](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Persistence/Durability/DurableSendingAgent.cs).

## Identity and idempotency gaps that configuration must close

1. **Deduplication scope:** `Durability.MessageIdentity` defaults to `IdOnly`. With one shared message store, independent module destinations receiving the same message ID can suppress each other. Configure `MessageIdentity.IdAndDestination` where storage is shared, or prove equivalent isolation through separate stores. Both selected database schemas implement destination as part of the primary key in that mode. The destination is an endpoint/subscription identity, not automatically a handler identity; independent effects need independently routed destinations or explicit handler-level idempotency. [Pinned enum and default](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/DurabilitySettings.cs), [PostgreSQL schema](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.Postgresql/Schema/IncomingEnvelopeTable.cs), [SQL Server schema](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.SqlServer/Schema/IncomingEnvelopeTable.cs).
2. **Finite protection:** the durable inbox retains handled envelopes for **five minutes by default**. This absorbs duplicates in a bounded window, not arbitrary later replay or external side effects. Keep every business handler safe for repeated source/event identity beyond the window. PostgreSQL inbox partitioning adds a status dimension to uniqueness and has documented race caveats; leave this optimization off in the initial recipe. [Pinned idempotency guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/durability/idempotency.md), [settings](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/DurabilitySettings.cs).
3. **Application event versus delivery identity:** Wolverine maps its envelope GUID to Azure `MessageId` and RabbitMQ AMQP `message-id`; resending a persisted envelope retains that identity. The catalog still needs an explicit mapping for source, stable event ID, event schema/version, occurred-at UTC, correlation/causation and entity identity. Prefer an application-owned immutable event/envelope representation plus a tested adapter. Republishing the same payload as a new send must not accidentally create a second business occurrence. The finite native inbox is insufficient if publication creates a new delivery GUID. [Azure mapper](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Transports/Azure/Wolverine.AzureServiceBus/Internal/AzureServiceBusEnvelopeMapper.cs), [RabbitMQ mapper](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Transports/RabbitMQ/Wolverine.RabbitMQ/Internal/RabbitMqEnvelopeMapper.cs), [delivery options](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/DeliveryOptions.cs).
4. **Logical deduplication is optional:** release source supports `DeduplicationId`, `[Deduplicated]` and a separately retained logical claim. It is an available mechanism, not automatic satisfaction of handler/subscription identity or indefinite business idempotency. Adopting it requires explicit key namespace, retention and transaction participation; use hash comparison if equivalent key behavior across PostgreSQL and SQL Server is required. [Pinned logical deduplication guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/durability/idempotency.md).
5. **Completion atomicity:** EF source explicitly writes handled-state in the selected context transaction and has regression tests for failed-attempt rollback and subsequent redelivery. It also checks whether the inbox row is actually in that context's store; another store cannot be assumed atomic. Crash after business commit but before completion bookkeeping remains a required integration scenario whenever the custom coordination path changes this ownership. [Pinned transaction source](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/Internals/EfCoreEnvelopeTransaction.cs), [SQL Server eager-idempotency regression tests](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/EfCoreTests/efcore_eager_idempotency_rides_the_handler_transaction.cs).

Azure broker duplicate detection is a separate, optional send-side window and is not a replacement for transactional consumer idempotency. It can also suppress an intentional same-ID resubmission during its window, including scheduled messages. A redrive procedure must account for this if enabled. [Microsoft duplicate-detection contract](https://learn.microsoft.com/en-us/azure/service-bus-messaging/duplicate-detection).

## Explicit routing and bounded failures

`InvokeAsync` can otherwise resolve to a remote request/reply route; set `EnableRemoteInvocation = false` in the retained fact-only messaging recipe. `SendAsync` and `PublishAsync` both use subscriptions; the former throws when none exists, while the latter may silently do nothing. Disable broad conventional local routing where it obscures the architecture, register allowed event routes explicitly, and verify the generated route table. A catalog publication adapter should fail for a required but unconfigured route. [Pinned bus guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/messaging/message-bus.md).

An immediate transactional module event cannot be implemented by merely publishing to a durable local queue: that is asynchronous and eventual. Keep a distinct explicit internal call path under the outer shared transaction. Externally published copies must be persisted through the outbox and become observable only after commit. Using the same fact schema for both routes must not cause accidental local delivery twice. This is an inference from the catalog contract and Wolverine's separate invocation/queued-delivery semantics; the cross-context transaction research determines the exact coordinator. [Catalog event resolution and amendments](https://github.com/lewan0996/arch-patterns/issues/20), [pinned bus semantics](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/messaging/message-bus.md).

Wolverine supports immediate retries, cooldown retries, scheduled retries, direct movement to an error destination and discard. A minimal candidate baseline is the retained two cooldown retries at **200 ms and 1 second**, then a terminal error destination; classified permanent failures go directly there. Configure this deliberately rather than adopting every default or indefinite retry option. These are three ordinary executions per failing cycle, not a lifetime bound: duplicates, crash recovery, operator replay and failed DLQ transfers may execute again. No Quartz, advanced delayed-redelivery profile or custom attempt journal is required. [Pinned error policies](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/handlers/error-handling.md), [retained scope](https://github.com/lewan0996/arch-patterns/issues/32).

Wolverine's durable receiver attempts the failure write before treating it as successful. If all failure-transfer attempts fail, it schedules the retained inbox message for another execution after 30 seconds and reports an error. Consequently even a permanently classified failure can execute again while its failure destination is unavailable; terminal visibility is not guaranteed during the outage. This is a concrete limitation to document and test, not a reason to add the deferred custom journal. [Pinned durable receiver](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Runtime/WorkerQueues/DurableReceiver.cs).

## Failure storage and operations

The default failure destination is transport/mode dependent. Azure inline queues use native source dead-letter subqueues; buffered/durable queues normally send failures to a Wolverine-managed error queue. Topic subscription native behavior must be checked separately. RabbitMQ native NACK dead lettering lacks detailed exception headers unless enhanced mode is enabled. Give every host distinct managed/system destinations; the unqualified `wolverine-dead-letter-queue` default is unsafe to share between unrelated services. [Pinned Azure failure guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/messaging/transports/azureservicebus/deadletterqueues.md), [Azure subscription model](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Transports/Azure/Wolverine.AzureServiceBus/Internal/AzureServiceBusSubscription.cs), [RabbitMQ failure guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/messaging/transports/rabbitmq/deadletterqueues.md).

A small coherent recipe can explicitly use the framework's database `wolverine_dead_letters` storage for application failures on durable queue endpoints by disabling native dead-letter queueing there. This is **standard framework storage**, not a custom journal. Alternatively retain host-specific native destinations and operate them directly, or bridge them using `EnableDeadLetterQueueRecovery`. The final choice is a human integration decision. Do not add both stores and a bridge reflexively. Native broker-generated failures such as max-delivery/TTL may still need separate inspection even when application failures use database storage. [Pinned failure-storage guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/durability/dead-letter-storage.md), [Azure endpoint storage model](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Transports/Azure/Wolverine.AzureServiceBus/Internal/AzureServiceBusQueue.cs).

Database failure expiry is opt-in; leave automatic expiry disabled initially. Standard `IDeadLetters`/CLI operations support inspection and replay without a paid dashboard. Preserve original application event identity on redrive and prove the actual destination/ID round trip; an HTTP management endpoint would require its own authentication and is not implied by this recommendation. Native Azure DLQs have no automatic cleanup, while a managed ordinary error queue has its own ordinary TTL settings; document both separately from handled-message dedup retention. [Pinned storage guide](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/docs/guide/durability/dead-letter-storage.md), [pinned replay operation](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.RDBMS/MessageDatabase.DeadLetterAdminService.cs), [Microsoft native DLQ retention](https://learn.microsoft.com/en-us/azure/service-bus-messaging/service-bus-dead-letter-queues).

## Comparison with the previous messaging recipe

The prior selected MassTransit 8.5.10 recipe already specified EF bus/consumer outboxes, module destinations, RabbitMQ local and Azure Service Bus production, two short retries, standard failure records and manual redrive. Wolverine changes framework mechanics rather than relaxing those requirements. Its native local durable queues and direct-service `IDbContextOutbox` can cover corresponding roles, but its default `IdOnly` scope, finite inbox window, endpoint-mode dependent DLQ handling and optional transaction selection must be made explicit. Immediate transactional module routing still needs its own shared transaction integration under either framework. No evidence found here establishes that Wolverine eliminates that integration work. [Previous technology resolution](https://github.com/lewan0996/arch-patterns/issues/13#issuecomment-6001651219), [previous failure recipe and scope amendments](https://github.com/lewan0996/arch-patterns/issues/32), [Wolverine pinned transaction source](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/Internals/EfCoreEnvelopeTransaction.cs).

## Smallest meaningful acceptance evidence

These are proposed implementation acceptance scenarios, not results obtained in this planning session. Share fixtures where behavior is identical, but keep separate provider and production transport outcomes.

| Fixture | Required evidence |
| --- | --- |
| EF transaction, each of PostgreSQL and SQL Server | State + outgoing envelope + applicable handled/processed marker all commit or roll back. Check persisted rows through a new connection; in-memory tracked-session success alone is insufficient. Cover direct-service explicit outbox and CQRS middleware paths. |
| Shared-host coordinator, both database providers | Two module-owned contexts change data, one immediate transactional module handler fails, and all writes/outgoing facts roll back. Success commits once and external facts appear only afterwards. Apply to modular-monolith and modular-microservice composition; coordinator details belong to the companion transaction investigation. |
| Managed Azure Service Bus + PostgreSQL | Crash after DB commit before broker send; broker-unavailable publication; lost/ambiguous send acknowledgement; restart recovery; durable inbox before broker settlement; crash after business commit; duplicate delivery; duplicate after inbox retention; terminal failure and manual redrive; failure destination unavailable. Assert no missing committed fact and no repeated business effect. |
| Managed Azure Service Bus + SQL Server | Repeat the boundaries that depend on provider persistence, completion and recovery. SQL Server support cannot be certified by PostgreSQL-only transport evidence or merely restoring its package. |
| Two subscriptions/modules in one host | The same source/event ID reaches both intended consumers once, a duplicate to either changes neither again, and one consumer's dedup record never suppresses the other. Prove `IdAndDestination` or the selected isolated-store design. |
| Envelope/routing contract | Type/version/source/ID/UTC time/correlation/causation/entity identity survive broker delivery and redrive; required missing route fails; internal-only does not publish externally; external-only does not accidentally invoke an internal transactional subscriber; no remote command/request-reply route exists. |
| Retry and failure operations | Transient and unknown failures follow the finite selected policy, permanent failure bypasses it, exact failure destination is observable, original identity survives repair/redrive, unrelated services do not drain each other's errors, and failure-transfer outage retains work visibly. |
| RabbitMQ local smoke, each supported provider | Publish/consume through durable configured endpoints, duplicate protection, error inspection/redrive, restart recovery and compatible envelope mapping. Mark this local evidence; it does not certify Azure semantics. |
| Durable local eventual module path | Persistence survives host restart, subscriber idempotency is independent, and its eventual outcome is clearly distinct from immediate rollback-capable routing. No additional broker or saga engine is needed. |

The initial recipe should promise no default global ordering, no end-to-end exactly-once delivery, no permanent outbox event archive and no full attempt history. Projection rebuild still needs the owner's explicit snapshot/backfill route. These preserve the [event-contract resolution and amendments](https://github.com/lewan0996/arch-patterns/issues/20) and the [bounded failure-recovery scope](https://github.com/lewan0996/arch-patterns/issues/32).
