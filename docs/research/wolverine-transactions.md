# Wolverine and shared-host module transactions

Research for [Investigate a minimal dispatcher, MediatR fork or Wolverine](https://github.com/lewan0996/arch-patterns/issues/37), checked 2026-11-15. This note covers transaction ownership, participating EF contexts and the outbox seam; it does not select the framework or claim runtime verification.

## Finding

Wolverine can persist messages through a caller-owned relational transaction. Its ordinary EF transactional middleware, however, selects **one** transactional context per handler chain. Registering several module contexts does not establish one atomic transaction across them. The retained catalog requirement therefore needs an explicit coordination recipe and a proof with both database providers; ordinary middleware configuration alone is insufficient. This is the same requirement in a modular monolith and in a modular microservice: both have several modules inside one deployable host. [Retained shared-host requirement](https://github.com/lewan0996/arch-patterns/issues/11#issuecomment-6885552758), [Wolverine context-selection implementation](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/Codegen/EFCorePersistenceFrameProvider.cs#L1120-L1194).

## What the built-in EF middleware actually establishes

- One context can combine business writes and Wolverine envelope storage in its transaction. The mapped path tracks envelope entities; the unmapped path writes envelope SQL through that context's connection and transaction. [EF envelope persistence source](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/Internals/EfCoreEnvelopeTransaction.cs#L54-L138).
- A chain with multiple context dependencies must explicitly designate its transaction context or fail. Upstream's PostgreSQL test deliberately verifies that only the designated context is enrolled and saved. It is a selection test, not multi-context atomicity proof. [Selection test](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/EfCoreTests/storage_dbcontext_selection_tests.cs#L25-L86).
- Reusing an already-open context transaction does not transfer commit ownership to an outer coordinator: the ordinary EF envelope commit still commits `CurrentTransaction`. Likewise, both `DbContextOutbox.SaveChangesAndFlushMessagesAsync` variants commit an existing context transaction. Calling either from a participating module can end the shared transaction prematurely. [EF middleware commit](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/Internals/EfCoreEnvelopeTransaction.cs#L333-L370), [outbox helper](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/DbContextOutbox.cs#L28-L41), [non-generic helper](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/DbContextOutbox.cs#L85-L104).

Lightweight mode is not a substitute for a shared transaction: individual `SaveChangesAsync` calls cannot atomically commit several independent contexts. Eager mode requires deliberate coordination with provider execution strategies. Wolverine rejects an eager handler paired with an implicitly retrying EF context rather than assuming the explicit transaction is replayable. [Transaction modes and validation](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.EntityFrameworkCore/Codegen/EFCorePersistenceFrameProvider.cs#L658-L701).

## Supported lower-level outbox seam

`DatabaseEnvelopeTransaction(IMessageDatabase, DbTransaction)` accepts an existing ADO.NET transaction. Its persistence methods write inbox/outbox records through that transaction; it does not commit or dispose it. The caller retains ownership. The SQL Server compliance sample opens a transaction, binds this adapter, performs the action, commits, and only then flushes outgoing messages. PostgreSQL has a regression test that explicitly preserves ownership when a pooled message context is later cleared. These are useful upstream source/test evidence, not a catalog multi-module runtime result. [Adapter](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.RDBMS/DatabaseEnvelopeTransaction.cs), [SQL Server sample](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/SqlServerTests/ScheduledJobs/SqlServerDurabilityCompliance.cs#L69-L95), [PostgreSQL ownership regression](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/PostgresqlTests/Bugs/an_enlisted_transaction_is_not_disposed_by_the_pooled_context.cs).

`EnlistInOutboxAsync(IEnvelopeTransaction)` is a public method on concrete `MessageBus`, inherited by `MessageContext`; **it is not declared by `IMessageContext`**. An integration adapter must use the actual exposed concrete API, not copy the sample's misleading interface comment. `StoreOutgoingAsync(DbTransaction, ...)` explicitly sets both command connection and transaction from the supplied transaction. [Enlist implementation](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Runtime/MessageBus.cs#L379-L395), [interface](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/IMessageContext.cs), [outbox SQL](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Persistence/Wolverine.RDBMS/MessageDatabase.Outgoing.cs#L18-L36).

Nested `InvokeAsync` is not evidence of transaction inheritance. The executor obtains another `MessageContext`, reads the new envelope and executes its handler; it does not copy the caller's transaction here. Any propagation of scope, module contexts, caller identity or outbox ownership must be made explicit and tested. An ambient variable alone is not evidence that separately resolved contexts actually share the connection and transaction. [Inline invocation](https://github.com/JasperFx/wolverine/blob/ccdf32562f6f53f01863d9fbb14886b8213f3ee2/src/Wolverine/Runtime/Handlers/Executor.cs#L145-L229).

## Proposed architectural seam — inference, pending proof

A host-integrated infrastructure coordinator can preserve module ownership without exposing another module's tables or contexts to application code:

1. Establish one operation scope, physical connection and transaction. Participating module infrastructure creates its own context over that connection and enlists with `UseTransactionAsync`.
2. Run the originating use case and drain its explicitly routed transactional facts through module-owned handler adapters sequentially in this scope. Handlers mutate only their module's model. Adapters preserve authorization/caller context and allow exceptions to fail the whole operation.
3. Bind one concrete Wolverine message context to `DatabaseEnvelopeTransaction` using message storage in that same database. External fact routes persist durable envelopes; immediate routes do not use durable queues as a replacement for before-commit execution.
4. Save every participating context, finish any newly raised immediate facts, then commit exactly once. Only the coordinator flushes outgoing messages after commit. Failure rolls back all writes and outgoing envelopes; participants cannot commit, independently flush or silently open another operation scope.

This is a design proposal composed from supported primitives. It still needs proof of invocation, event draining, inbox handling and restart recovery as one recipe. Generated EF transaction middleware and per-module save-and-flush helpers must not independently own this path. A custom adapter is additional integration work even if no framework fork is needed. The same adapter must work when the originating use case uses direct services rather than CQRS dispatch.

EF requires shared contexts to use the same **connection object and transaction**, not merely equal connection strings. This limits the operation to compatible contexts in the same relational database. Preserve private schemas and migrations. Do not infer distributed transactions across independently deployed services. [EF cross-context and external transaction documentation](https://learn.microsoft.com/en-us/ef/core/saving/transactions#cross-context-transaction).

If provider retries are enabled, replay the entire unit with new operation state under the chosen execution strategy; do not retry only the final context save. Resolve ambiguous commit outcomes with idempotency or verification. [EF execution strategies and commit ambiguity](https://learn.microsoft.com/en-us/ef/core/miscellaneous/connection-resiliency#execution-strategies-and-transactions).

## Comparison with the prior provisional combination

Changing to MediatR plus MassTransit does not make cross-module coordination automatic. MassTransit v8.5.12's EF bus-outbox provider is generic in one `TDbContext`; its consumer outbox context holds one context and one transaction and saves that context. This supports the familiar state/outbox unit, while a shared connection/transaction coordinator still has to enlist the other module contexts. MediatR dispatch itself provides no relational transaction; its dispatcher resolves and invokes request wrappers through the supplied service provider. [MediatR 12.5.0 dispatcher](https://github.com/jbogard/MediatR/blob/v12.5.0/src/MediatR/Mediator.cs). Evaluate a fallback against the same proof criteria. Do not backport configuration from the moving v9 documentation into a v8 recipe. [v8 EF bus context provider](https://github.com/MassTransit/MassTransit/blob/v8.5.12/src/Persistence/MassTransit.EntityFrameworkCoreIntegration/EntityFrameworkCoreIntegration/EntityFrameworkScopedBusContextProvider.cs), [v8 consumer outbox context](https://github.com/MassTransit/MassTransit/blob/v8.5.12/src/Persistence/MassTransit.EntityFrameworkCoreIntegration/EntityFrameworkCoreIntegration/DbContextOutboxConsumeContext.cs), [current documentation version distinction](https://masstransit.massient.com/configuration/middleware/outbox).

## Smallest meaningful proof set

These are proposed acceptance checks, **not tests run in this research**:

- Two real contexts with separate private schemas, over one real PostgreSQL database; repeat on real SQL Server. Assert connection identity, transaction identity and exactly one commit owner.
- Originating module write → immediate fact → second-module write → external fact. Successful commit persists both business changes and outgoing envelope; no broker delivery occurs before commit.
- Throw after the second module has saved, and separately during a later fact handler. Both modules and the outbox remain unchanged; no external event escapes. Include nested fact emission and cancellation.
- Cover HTTP and non-HTTP entry points, CQRS and direct-service invocation, and both shared-host layouts; verify that none creates a second transaction or bypasses module authorization.
- Kill the process after commit and before flush. Restart sends the durable external event. For received events, duplicate delivery does not repeat committed business effects; test actual chosen inbox handling rather than inferring it from outbox enlistment.
- Exercise the provider retry policy and a commit-acknowledgment failure; confirm whole-unit replay or explicit uncertain-outcome handling.
- Reject a participant configured against another database/provider, missing module registration and premature participant commit/flush. Verify per-module migration ownership and message-table migration ownership explicitly.

Production Azure Service Bus evidence is additionally required for the full framework choice; RabbitMQ success cannot establish it. That transport investigation is separate from the transaction primitives researched here.
